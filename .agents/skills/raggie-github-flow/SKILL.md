# GitHub-поток Raggie

Репозиторий: `Isotere/raggie`. Основная ветка: `master`.

Используй `git` для локального состояния и `gh` для GitHub. Не выводи и не сохраняй токены.

## Общие проверки

Перед изменением:

1. проверь `git status --short --branch`;
2. проверь remote и текущую ветку;
3. прочитай issue через `gh issue view`;
4. остановись, если незакоммиченные изменения могут потеряться или попасть не в ту задачу;
5. проверь, что `core.hooksPath` указывает на `.githooks`, а author и committer используют GitHub noreply email;
6. проверь staged или публикуемый diff на секреты, PII, закрытые данные и абсолютные локальные пути;
7. не откатывай пользовательские изменения.

Read-only проверка не разрешает менять GitHub. Ветка, push, PR, review, изменение полей GitHub Project, закрытие issue и merge требуют прямого запроса на соответствующее действие.

## Создание ветки под issue

При прямом запросе создать ветку:

1. определи номер issue и короткое имя;
2. убедись, что base — `master`, если пользователь не указал другую ветку;
3. предпочитай `gh issue develop`, чтобы связать ветку с issue;
4. используй имя `issue-<номер>-<краткое-название>`;
5. переключись на ветку и покажи итоговый статус.

Не меняй статус, итерацию или другие поля GitHub Project без отдельного запроса.

## Создание pull request

При прямом запросе создать PR:

1. проверь, что текущая ветка не `master`;
2. изучи diff и commits относительно base;
3. запусти относящиеся к изменению проверки;
4. не исправляй найденные ошибки без отдельного запроса;
5. при незакоммиченных изменениях не создавай commit автоматически;
6. отправь ветку в `origin`, если push входит в запрос на создание PR;
7. создай PR с результатом, проверками и известными ограничениями;
8. добавь `Closes #<номер>`;
9. покажи URL и состояние проверок.

Соглашение:

```text
Ветка:  issue-<номер>-<краткое-название>
Commit: <type>: <изменение> (#<номер>)
PR body: Closes #<номер>
```

Не выполняй merge, не закрывай issue вручную и не отправляй approve собственному PR. Сбой сети или авторизации не обходи альтернативной публикацией: сообщи причину.

Не используй `--no-verify`. Hook проверяет Git identity, но не заменяет просмотр публикуемого содержимого.
