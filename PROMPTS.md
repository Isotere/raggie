# Рабочие промпты Raggie

Файл содержит короткие запросы для сессий Codex из корня Raggie. Правила `AGENTS.md` действуют всегда; промпт задаёт конкретную задачу и разрешённые действия.

Текст в угловых скобках нужно заменить своими данными. Запросы «проверь», «объясни», «спланируй» и «проведи ревью» не разрешают менять файлы, GitHub или vault.

## 1. Начать рабочую сессию

```text
Проверь текущее состояние Raggie.

1. Прочитай AGENTS.md.
2. Покажи текущую ветку и состояние рабочего дерева.
3. Если ветка связана с GitHub Issue, прочитай задачу.
4. Определи текущий этап по доступной документации vault.
5. Кратко перечисли имеющиеся артефакты и ближайший проверяемый результат.

Ничего не изменяй, не создавай ветки и не проектируй следующие этапы.
```

## 2. Разобрать тему Rust

```text
Объясни тему Rust: <тема>.

Контекст: <где тема встретилась в Raggie или курсе>.
Что я уже понимаю: <текущие знания>.

Раскрой:
1. какую проблему решает механизм;
2. как он работает на уровне, достаточном для текущей задачи;
3. чем отличается от ближайшего аналога в Go;
4. какие ошибки типичны;
5. как проверить понимание на небольшой самостоятельной практике.

Не решай задачу Raggie за меня. Изолированный пример допустим только для объяснения механизма.
```

## 3. Разобрать тему баз данных или векторного поиска

```text
Объясни тему: <тема СУБД или векторного поиска>.

Контекст этапа Raggie: <задача и границы>.
Что я уже понимаю: <текущие знания>.

Раскрой решаемую проблему, модель, инварианты, основные альтернативы, компромиссы и способы проверки. Отдели общую теорию от решений, уже зафиксированных для Raggie. Используй первичные или официальные источники.

Не проектируй реализацию за меня и не меняй файлы.
```

## 4. Получить одну подсказку

```text
Я решаю задачу самостоятельно и застрял.

Задача: <описание>.
Что уже сделал: <действия>.
Что ожидал: <результат>.
Что получил: <результат или ошибка>.

Дай одну следующую подсказку. Не пиши код и не раскрывай полное решение. Если данных недостаточно, задай один конкретный вопрос.
```

## 5. Разобрать ошибку компилятора

```text
Помоги понять ошибку компилятора Rust.

Команда: <команда>.
Сообщение компилятора:
<полный текст>

Связанные файлы: <пути>.

Объясни первопричину, нарушенное правило Rust и вторичные сообщения. Назови направления исправления и их компромиссы.

Не изменяй файлы и не пиши исправленный код: сначала я попробую исправить ошибку сам.
```

## 6. Выделить следующую задачу этапа

```text
Используй $raggie-stage-plan.

Помоги выделить следующую небольшую задачу текущего этапа Raggie.

Текущее состояние: <что уже готово>.
Ближайший результат этапа: <результат>.
Доступное время: <часы или занятия>.
Изученные темы Rust и баз данных: <темы>.

Задача должна иметь один наблюдаемый результат, понятные входы, границы и критерии завершения. Не добавляй скрытую подготовительную работу и не описывай реализацию.

Пока ничего не изменяй в репозитории и vault.
```

## 7. Детализировать этап

```text
Используй $raggie-stage-plan.

Детализируй этап Raggie: <номер и название>.

Прочитай описание проекта, верхнеуровневые этапы, организацию монорепозитория, программу изучения и фактический результат предыдущего этапа.

Опиши исходную точку, пользовательский сценарий, контракт, входы, границы, ожидаемые результаты, последовательность работы, риски и критерии завершения. Разбей этап на задачи, выполнимые одним человеком за разумное время.

Обнови документ этапа в vault. Не создавай GitHub Issues и не переходи к реализации.
```

## 8. Проверить завершение задачи или этапа

```text
Используй $raggie-stage-plan.

Проверь завершение <задачи или этапа>.

Критерии: <критерии или путь к документу>.
Полученный результат: <файлы, команды, тесты, измерения и наблюдения>.
Известные ограничения: <ограничения>.

Сопоставь критерии с подтверждённым результатом. Верни одно решение:
- завершено;
- не завершено: назови недостающий проверяемый результат;
- критерий больше не нужен: объясни причину.

Не изменяй файлы.
```

## 9. Создать учебный конспект

```text
Используй $raggie-learning-note.

Создай или обнови конспект по теме: <тема>.

Источник: <курс, книга, статья, документация или мои заметки>.
Раздел материалов: <Rust, Базы данных, Консоль и VIM>.
Связь с текущим этапом: <задача>.
Что нужно раскрыть: <вопросы>.

Проверь существующие конспекты, чтобы не дублировать материал. Отдели содержание источника от дополнительных пояснений и решений Raggie.

Обнови соответствующий файл в vault. Код Raggie не изменяй.
```

## 10. Обновить документацию или результат этапа в vault

```text
Используй $raggie-vault-docs.

Обнови документацию Raggie в vault.

Целевой документ: <путь>.
Что произошло: <подтверждённые факты>.
Доказательства: <файлы, commits, команды, тесты, измерения или наблюдения>.
Известные ограничения: <ограничения>.

Зафиксируй только подтверждённый результат. Не выдавай планы за выполненную работу. Проверь термины и при необходимости обнови словарь.

Репозиторий не изменяй.
```

## 11. Провести ревью локальных изменений

```text
Используй $raggie-code-review.

Проведи ревью <рабочего дерева, staged diff или текущей ветки>.

Связанная задача: <номер issue или описание>.
Критерии готовности: <критерии>.

Проверь корректность, численные граничные случаи, обработку ошибок, тесты, владение, публичный контракт и инварианты текущего этапа Raggie. Сначала перечисли замечания по убыванию серьёзности с файлом и строкой.

Не изменяй файлы и не отправляй review в GitHub.
```

## 12. Создать ветку для GitHub Issue

```text
Используй $raggie-github-flow.

Создай связанную рабочую ветку для issue № <номер>.

1. Проверь рабочее дерево и прочитай issue.
2. Используй master как base.
3. Создай ветку через gh issue develop по соглашению issue-<номер>-<краткое-название>.
4. Переключись на неё и покажи итоговый статус.

Не изменяй код, статус issue, итерацию или поля GitHub Project.
```

## 13. Подготовить pull request

```text
Используй $raggie-github-flow.

Создай pull request из текущей ветки для issue № <номер>.

Проверь diff, commits и относящиеся к задаче проверки. Если рабочее дерево содержит незакоммиченные изменения или проверки не проходят, остановись: ничего не исправляй и не создавай commit самостоятельно.

Если ветка готова, отправь её в origin и создай PR в master. В описании укажи результат, выполненные проверки, известные ограничения и Closes #<номер>.

Не выполняй merge и не закрывай issue вручную.
```

## 14. Диагностировать сбой CI

```text
Диагностируй сбой GitHub Actions для <PR или run ID>.

Прочитай workflow и логи упавших jobs. Отдели первичную ошибку от последующих сбоев. Составь гипотезы по убыванию вероятности и для каждой предложи минимальную проверку.

Не запускай workflow повторно, не меняй файлы и не предлагай исправление, пока причина не подтверждена.
```

## 15. Прямо поручить реализацию Codex

Этот промпт нужен, когда код или конфигурацию должен написать Codex.

```text
Реализуй изменение: <точное описание>.

Связанная issue: <номер>.
Разрешённая область изменений: <файлы или каталоги>.
Не изменять: <ограничения>.
Критерии готовности: <проверяемые критерии>.

Перед изменением прочитай AGENTS.md, issue и существующие соглашения. Не выполняй побочные рефакторинги и не добавляй возможности сверх задачи.

После изменения запусти относящиеся к задаче проверки. Не создавай commit, push или PR без отдельного запроса. Перечисли изменённые файлы, подтверждённое поведение и оставшиеся ограничения.
```
